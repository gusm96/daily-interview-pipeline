## Java 스레드 안전성 문제 및 해결 기법

### 1. 핵심 정의

Java에서 여러 스레드가 공유 자원(변수, 객체, 파일 등)에 동시에 접근하여 읽거나 쓸 때, 예상치 못한 결과나 데이터 불일치가 발생하는 것을 **경쟁 조건(Race Condition)**이라고 합니다. 이러한 문제를 방지하고 프로그램의 정확성을 보장하는 것을 **스레드 안전성(Thread Safety)** 확보라고 합니다.

### 2. 동작 원리 및 문제점

*   **경쟁 조건**: 여러 스레드가 공유 자원에 동시에 접근하여 최종 결과가 스레드 실행 순서에 따라 달라지는 상황입니다.
*   **데이터 불일치**: 한 스레드가 자원을 업데이트하는 도중에 다른 스레드가 해당 자원을 읽거나 업데이트하여 데이터가 손상되거나 일관성이 깨지는 문제입니다.
*   **데드락(Deadlock)**: 두 개 이상의 스레드가 서로가 가진 자원을 기다리며 무한히 대기하는 상태입니다.
*   **라이브락(Livelock)**: 스레드들이 서로의 작업을 방해하지 않으려고 계속 상태를 변경하지만, 결국 아무 작업도 진행되지 못하는 상태입니다.
*   **기아(Starvation)**: 특정 스레드가 자원을 얻지 못해 작업을 영원히 수행하지 못하는 상태입니다.

### 3. 스레드 안전성 보장 기법 비교

| 기법 | 장점 | 단점 | 적절한 사용 시나리오 |
| :--- | :--- | :--- | :--- |
| **`synchronized` 키워드** | - 사용이 간편하고 직관적임<br>- JVM 레벨에서 동작하여 안정적임 | - 성능 오버헤드가 발생할 수 있음<br>- 락의 범위가 넓어지면 병렬성 저하 | - 메서드 전체 또는 특정 코드 블록에 대한 간단한 동기화<br>- 공유 객체의 상태 변경이 빈번하지 않을 때 |
| **`java.util.concurrent.locks.Lock` 인터페이스 (예: `ReentrantLock`)** | - `synchronized`보다 유연한 락 제어 (타임아웃, 조건 변수 등)<br>- 명시적인 락 획득/해제 | - `finally` 블록을 통한 락 해제 필수 (누락 시 데드락 위험)<br>- `synchronized`보다 복잡한 코드 | - 복잡한 동기화 로직이 필요할 때<br>- 락 획득 시도에 타임아웃을 주고 싶을 때<br>- 읽기/쓰기 락 분리가 필요할 때 (`ReadWriteLock`) |
| **`java.util.concurrent.atomic` 패키지** | - 락 없이 원자적 연산 보장 (CAS)<br>- 높은 성능과 확장성 | - 복잡한 연산에는 적용하기 어려움<br>- 모든 데이터 타입에 적용 가능한 것은 아님 | - 단일 변수에 대한 원자적 업데이트 (카운터, 플래그 등)<br>- 락 오버헤드를 피하고 싶을 때 |
| **`volatile` 키워드** | - 가시성(Visibility) 보장<br>- 락 없이 사용 가능 | - 원자성(Atomicity)은 보장하지 않음<br>- 재정렬(Reordering) 방지 | - 여러 스레드가 공유 변수를 읽기만 하고, 한 스레드만 쓰는 경우<br>- 플래그 변수처럼 최신 값의 가시성이 중요한 경우 |
| **불변 객체(Immutable Object)** | - 스레드 안전성이 기본적으로 보장됨<br>- 동기화 로직 불필요 | - 객체 상태 변경 시 새로운 객체 생성 필요 (메모리 오버헤드)<br>- 모든 객체를 불변으로 만들기는 어려움 | - 한 번 생성되면 상태가 변하지 않는 객체 (예: `String`, `Integer`)<br>- 캐싱, 공유 데이터에 적합 |
| **스레드 로컬(ThreadLocal)** | - 각 스레드마다 독립적인 변수 공간 제공<br>- 공유 자원 접근 문제 회피 | - 메모리 누수 위험 (제거하지 않을 경우)<br>- 스레드 간 데이터 공유 불가 | - 각 스레드별로 독립적인 세션 정보, 사용자 정보 등을 저장할 때<br>- 데이터베이스 연결 객체 등 스레드마다 고유한 리소스가 필요할 때 |

### 4. 실무에서 주의할 점

*   **최소한의 락 범위**: 락은 필요한 최소한의 코드 블록에만 적용하여 병렬성을 최대한 확보해야 합니다. 락의 범위가 넓어지면 병목 현상이 발생하기 쉽습니다.
*   **데드락 방지**: 락을 획득하는 순서를 일관되게 유지하고, 타임아웃을 설정하거나 `tryLock()`과 같은 비블로킹 락 획득 방식을 고려하여 데드락 발생 가능성을 줄여야 합니다.
*   **성능 고려**: 동기화 기법은 오버헤드를 발생시키므로, 성능 요구사항을 고려하여 가장 적절하고 효율적인 기법을 선택해야 합니다. `atomic` 패키지나 불변 객체 사용을 우선적으로 고려할 수 있습니다.
*   **메모리 가시성**: `volatile` 키워드나 `synchronized` 블록을 통해 메모리 가시성을 확보하여, 한 스레드의 변경 사항이 다른 스레드에게 즉시 보이도록 해야 합니다.
*   **테스트**: 스레드 안전성 문제는 재현하기 어렵고 디버깅이 까다로우므로, 철저한 단위 테스트와 통합 테스트를 통해 잠재적인 경쟁 조건을 미리 발견하고 해결해야 합니다.
*   **`ThreadLocal` 사용 시 주의**: `ThreadLocal` 변수는 스레드가 종료될 때 명시적으로 `remove()` 해주지 않으면 메모리 누수가 발생할 수 있으므로 주의해야 합니다.
