## OutOfMemoryError (OOM) 발생 시 힙 영역 문제 진단 및 해결

### 1. 핵심 정의

`OutOfMemoryError`는 JVM이 더 이상 객체를 할당할 수 있는 충분한 메모리를 찾지 못할 때 발생하는 치명적인 오류입니다. 특히 힙(Heap) 영역에서 발생하는 OOM은 대부분 애플리케이션이 필요로 하는 객체 저장 공간이 JVM에 할당된 힙 메모리 크기를 초과할 때 발생합니다.

### 2. 동작 원리 (힙 영역 문제)

힙 영역에서 OOM이 발생하는 주요 원인은 다음과 같습니다.

*   **메모리 누수 (Memory Leak):** 더 이상 사용되지 않는 객체가 가비지 컬렉션(GC) 대상에서 제외되지 않고 계속 힙에 남아있어 메모리가 점진적으로 고갈되는 현상입니다. 예를 들어, static 컬렉션에 객체를 계속 추가하거나, 이벤트 리스너를 등록 후 해제하지 않는 경우 발생할 수 있습니다.
*   **과도한 객체 생성:** 짧은 시간 내에 매우 많은 수의 객체를 생성하거나, 각 객체의 크기가 매우 커서 힙 공간을 빠르게 소진하는 경우입니다. 대용량 데이터를 한 번에 로딩하거나, 불필요하게 큰 객체를 반복적으로 생성할 때 발생할 수 있습니다.
*   **힙 설정 부족:** 애플리케이션의 실제 메모리 요구량에 비해 JVM에 할당된 힙 메모리(Xmx)가 너무 작게 설정된 경우입니다.

### 3. 실무에서 진단 및 해결 방법

OOM 발생 시 힙 영역 문제를 진단하고 해결하기 위한 구체적인 도구와 접근 방식은 다음과 같습니다.

#### 진단 방법

1.  **JVM 로그 분석:**
    *   **GC 로그:** `-Xloggc:<file-path>` 또는 최신 JVM의 `-Xlog:gc*` 옵션을 통해 GC 로그를 활성화합니다. GC 발생 빈도, 소요 시간, 힙 사용량 변화 등을 분석하여 메모리 누수 징후나 비효율적인 GC를 파악할 수 있습니다.
    *   **OOM 메시지:** OOM 발생 시 출력되는 메시지에는 어떤 영역에서 OOM이 발생했는지(e.g., Java heap space, Metaspace)에 대한 힌트가 포함되어 있습니다.

2.  **힙 덤프 (Heap Dump) 분석:**
    *   **힙 덤프 생성:** OOM 발생 시 자동으로 힙 덤프를 생성하도록 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=<path>` 옵션을 설정합니다. 또는 `jmap -dump:format=b,file=<file-path> <pid>` 명령어를 사용하여 수동으로 생성할 수 있습니다.
    *   **힙 덤프 분석 도구:**
        *   **Eclipse Memory Analyzer Tool (MAT):** 가장 널리 사용되는 도구 중 하나로, 힙 덤프를 로드하여 메모리 누수 의심 객체(Leak Suspects), 가장 많은 메모리를 점유하는 객체(Top Consumers), 객체 참조 경로 등을 시각적으로 분석할 수 있습니다.
        *   **VisualVM:** JVM 모니터링 도구로, 힙 덤프를 로드하여 클래스별 인스턴스 수, 메모리 사용량 등을 확인할 수 있습니다.

3.  **실시간 모니터링:**
    *   **JConsole/VisualVM:** 애플리케이션 실행 중 힙 사용량, GC 활동 등을 실시간으로 모니터링하여 메모리 사용 패턴을 파악하고 이상 징후를 조기에 감지할 수 있습니다.
    *   **APM (Application Performance Monitoring) 도구:** 상용 APM 도구(e.g., New Relic, Dynatrace, Pinpoint)는 JVM 메모리 사용량, GC 통계 등을 포함한 상세한 성능 지표를 제공하여 OOM 발생 전후의 상황을 종합적으로 분석하는 데 도움을 줍니다.

#### 해결 방법

1.  **메모리 누수 해결:**
    *   힙 덤프 분석을 통해 누수 원인으로 지목된 객체와 그 참조 경로를 파악합니다.
    *   코드 레벨에서 더 이상 사용되지 않는 객체의 참조를 명시적으로 `null`로 설정하거나, 컬렉션에서 제거, 리스너 등록 해제 등을 통해 GC 대상이 되도록 수정합니다.
    *   특히 `static` 필드나 장기 실행 스레드에서 객체 참조가 유지되지 않도록 주의합니다.

2.  **객체 생성 최적화:**
    *   불필요한 객체 생성을 줄입니다. (e.g., String concatenation 대신 `StringBuilder`/`StringBuffer` 사용)
    *   객체 풀링(Object Pooling) 기법을 사용하여 객체 재사용을 고려합니다.
    *   대용량 데이터를 처리할 때는 스트리밍 방식이나 페이지네이션을 적용하여 한 번에 로딩하는 데이터 양을 줄입니다.
    *   원시 타입 배열 대신 `ArrayList`와 같은 동적 컬렉션을 사용할 때, 초기 용량을 적절히 설정하여 불필요한 배열 복사를 줄입니다.

3.  **JVM 힙 설정 조정:**
    *   애플리케이션의 실제 메모리 요구량을 충분히 고려하여 `-Xmx` (최대 힙 크기) 값을 적절히 증설합니다. 일반적으로 운영 환경에서는 물리 메모리의 50~80% 수준으로 설정하는 경우가 많습니다.
    *   `-Xms` (초기 힙 크기)를 `-Xmx`와 동일하게 설정하여 힙 확장에 따른 GC 오버헤드를 줄일 수 있습니다.
    *   GC 알고리즘(e.g., G1GC, ParallelGC)을 애플리케이션 특성에 맞게 선택하고, 관련 옵션(e.g., `-XX:MaxGCPauseMillis`)을 튜닝하여 GC 성능을 최적화합니다.

이러한 진단 및 해결 방법을 통해 OOM의 근본 원인을 파악하고 안정적인 애플리케이션 운영을 도모할 수 있습니다.
