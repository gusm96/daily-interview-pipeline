## Java 가비지 컬렉터(GC) 특징 및 선택 가이드

안녕하세요! Java 가비지 컬렉터는 JVM의 핵심 구성 요소 중 하나로, 메모리 관리를 자동화하여 개발자가 메모리 누수나 해제에 대한 부담 없이 비즈니스 로직에 집중할 수 있도록 돕습니다. 다양한 GC 알고리즘은 각각 다른 목표와 트레이드오프를 가지고 있습니다.

### 1. 가비지 컬렉터별 특징 및 동작 방식

Java의 주요 가비지 컬렉터들은 Stop-The-World(STW) 시간을 최소화하거나 처리량을 극대화하는 등 각기 다른 목표를 가지고 설계되었습니다.

*   **Serial GC**
    *   **핵심 정의:** 단일 스레드로 모든 GC 작업을 수행하는 가장 기본적인 가비지 컬렉터입니다.
    *   **동작 원리:** 애플리케이션 스레드를 모두 중단(STW)시킨 후, 힙 전체를 스캔하고 사용되지 않는 객체를 회수합니다.
    *   **실무에서 주의할 점:** CPU 코어가 하나이거나, 힙 사이즈가 매우 작아 STW 시간이 허용 가능한 수준일 때 적합합니다. 일반적으로 서버 환경에서는 잘 사용되지 않습니다.

*   **Parallel GC (Throughput Collector)**
    *   **핵심 정의:** 여러 스레드를 사용하여 Young Generation의 GC 작업을 병렬로 처리하여 처리량(Throughput)을 높이는 데 중점을 둔 가비지 컬렉터입니다.
    *   **동작 원리:** Young Generation GC 시 여러 스레드가 동시에 작업을 수행하여 STW 시간을 단축합니다. Old Generation GC는 일반적으로 단일 스레드로 수행되거나, 병렬로 수행될 수도 있습니다.
    *   **실무에서 주의할 점:** 전체 애플리케이션의 처리량이 중요한 배치 처리와 같은 애플리케이션에 적합합니다. STW 시간이 길어질 수 있어 대화형 애플리케이션에는 부적합할 수 있습니다.

*   **CMS GC (Concurrent Mark Sweep Collector)**
    *   **핵심 정의:** 애플리케이션 스레드와 GC 스레드가 동시에(Concurrent) 작업을 수행하여 STW 시간을 최소화하는 데 중점을 둔 가비지 컬렉터입니다.
    *   **동작 원리:** 초기 마크(Initial Mark)와 재마크(Remark) 단계에서만 STW가 발생하고, 대부분의 마킹 및 스윕(Sweep) 작업은 애플리케이션 스레드와 동시에 진행됩니다. 단, 단편화(Fragmentation) 문제가 발생할 수 있습니다.
    *   **실무에서 주의할 점:** 응답 시간이 중요한 웹 서버나 UI 애플리케이션에 적합합니다. 하지만 단편화로 인해 Full GC가 발생할 수 있으며, GC 스레드가 CPU 리소스를 사용하므로 처리량 감소가 발생할 수 있습니다. Java 9부터 Deprecated 되었고, Java 14부터는 제거되었습니다.

*   **G1 GC (Garbage-First Collector)**
    *   **핵심 정의:** 힙을 Region이라는 작은 단위로 나누어 관리하며, 가장 효율적인(가장 많은 가비지를 포함하는) Region부터 우선적으로 수집하여 STW 시간을 최소화하면서도 높은 처리량을 목표로 하는 가비지 컬렉터입니다.
    *   **동작 원리:** 힙을 Region으로 나누고, 각 Region의 가비지 양을 추적합니다. GC 시에는 STW를 발생시켜 가장 많은 가비지를 가진 Region들을 병렬로 수집합니다. Young/Old Generation의 개념이 논리적으로 존재하지만, 물리적으로는 Region들이 동적으로 할당됩니다.
    *   **실무에서 주의할 점:** 대용량 힙(4GB 이상)을 사용하는 애플리케이션에서 낮은 지연 시간과 높은 처리량을 모두 만족시키고자 할 때 적합합니다. 대부분의 최신 Java 애플리케이션에서 기본 GC로 사용됩니다.

### 2. 애플리케이션 요구사항에 따른 GC 선택

애플리케이션의 주요 요구사항(처리량, 지연 시간)에 따라 적절한 GC를 선택하는 것이 중요합니다.

*   **높은 처리량(Throughput)이 중요한 경우:**
    *   **선택:** **Parallel GC**
    *   **이유:** 배치 처리, 데이터 분석 등 전체 작업 완료 시간이 중요한 애플리케이션에서는 STW 시간이 길어져도 전체 처리량을 극대화하는 Parallel GC가 유리합니다. 여러 CPU 코어를 활용하여 GC 작업을 병렬로 처리함으로써 애플리케이션의 유휴 시간을 줄이고 더 많은 작업을 수행할 수 있습니다.

*   **낮은 지연 시간(Low Latency) 또는 짧은 응답 시간이 중요한 경우:**
    *   **선택:** **G1 GC** (또는 ZGC, Shenandoah와 같은 최신 GC)
    *   **이유:** 웹 서버, 실시간 시스템, UI 애플리케이션 등 사용자 응답성이 중요한 애플리케이션에서는 GC로 인한 STW 시간을 최소화해야 합니다. G1 GC는 힙을 Region으로 나누고 예측 가능한 STW 시간을 목표로 하여, 대용량 힙에서도 짧은 지연 시간을 제공합니다. CMS GC도 낮은 지연 시간을 목표로 했지만, 단편화 문제와 Deprecated 이슈로 인해 G1 GC가 더 권장됩니다.

*   **일반적인 대용량 힙 애플리케이션:**
    *   **선택:** **G1 GC**
    *   **이유:** G1 GC는 대부분의 현대적인 Java 애플리케이션에서 좋은 성능을 보여주며, 낮은 지연 시간과 높은 처리량 사이의 균형을 잘 맞춥니다. 특별한 요구사항이 없다면 G1 GC를 기본으로 고려하는 것이 좋습니다.

GC 선택은 애플리케이션의 특성, 힙 크기, CPU 코어 수 등 다양한 요소를 고려해야 하며, 실제 운영 환경에서 프로파일링을 통해 최적의 GC를 찾는 것이 가장 중요합니다.
