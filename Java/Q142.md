# [Q142] Java 힙 영역의 Young/Old Generation과 GC 튜닝

### 1. Java 힙 메모리가 Young Generation과 Old Generation으로 나뉘는 이유

**핵심 정의:** Java 힙 메모리는 객체의 생명 주기에 따라 효율적인 가비지 컬렉션을 위해 Young Generation과 Old Generation으로 논리적으로 분할됩니다.

**동작 원리:**
*   **Young Generation:** 대부분의 객체는 생성된 직후 빠르게 접근 불가능 상태가 됩니다. Young Generation은 이러한 단명(short-lived) 객체들을 효율적으로 처리하기 위해 설계되었습니다.
*   **Old Generation:** Young Generation에서 여러 번의 GC에도 불구하고 살아남은 객체들은 비교적 오래 생존할 가능성이 높다고 판단되어 Old Generation으로 이동합니다. 이는 장명(long-lived) 객체들을 위한 공간입니다.
*   **분할 이유:** 객체의 생명 주기가 다르다는 통계적 특성(Weak Generational Hypothesis)을 활용하여, 각 영역에 최적화된 GC 알고리즘을 적용함으로써 전체 GC 오버헤드를 줄이고 애플리케이션 처리량을 향상시키기 위함입니다.

**실무에서 주의할 점:**
*   Young Generation의 크기가 너무 작으면 객체가 너무 빨리 Old Generation으로 승격되어 Old GC 빈도가 높아질 수 있습니다.
*   Old Generation의 크기가 너무 작으면 Full GC가 자주 발생하여 애플리케이션 성능에 심각한 영향을 줄 수 있습니다.

---

### 2. 각 영역에서 발생하는 GC의 종류 및 동작 방식

**핵심 정의:** Young Generation에서는 Minor GC가, Old Generation에서는 Major GC (또는 Full GC의 일부)가 발생하며, 각각 다른 알고리즘을 사용합니다.

**동작 원리:**

*   **Young Generation (Minor GC):**
    *   **종류:** 일반적으로 Copying Collector (예: Serial, Parallel, G1의 Young GC)가 사용됩니다.
    *   **동작 방식:**
        *   Young Generation은 Eden, Survivor 0 (S0), Survivor 1 (S1) 세 개의 공간으로 나뉩니다.
        *   새로운 객체는 Eden 영역에 할당됩니다.
        *   Eden 영역이 가득 차면 Minor GC가 발생합니다.
        *   Eden과 S0 (또는 S1)에서 살아남은 객체는 다른 Survivor 영역으로 복사되고, 객체의 Age(생존 횟수)가 증가합니다.
        *   복사된 객체들이 특정 Age 임계값을 넘으면 Old Generation으로 승격(Promotion)됩니다.
        *   GC가 완료되면 사용되지 않은 Eden과 이전 Survivor 영역은 비워집니다.
    *   **특징:** 대부분의 객체가 빠르게 소멸되므로, 살아남은 객체만 복사하는 방식이 효율적입니다. Stop-The-World(STW) 시간이 짧습니다.

*   **Old Generation (Major GC / Full GC):**
    *   **종류:** Mark-Sweep-Compact (표시-쓸기-압축) 방식의 Collector (예: Serial, Parallel, CMS, G1의 Old GC)가 사용됩니다.
    *   **동작 방식:**
        *   **Mark (표시):** Root Set에서부터 참조 가능한 모든 객체를 찾아 표시합니다.
        *   **Sweep (쓸기):** 표시되지 않은(참조 불가능한) 객체들을 힙에서 제거합니다. 이 과정에서 메모리 단편화가 발생할 수 있습니다.
        *   **Compact (압축):** 단편화를 해소하기 위해 살아남은 객체들을 힙의 한쪽으로 모아 재배치합니다. 이 단계는 모든 GC에서 필수는 아니며, 일부 GC는 압축을 수행하지 않거나 선택적으로 수행합니다.
    *   **특징:** Young Generation에 비해 객체 수가 많고 오래 살아남으므로, Minor GC보다 STW 시간이 길고 비용이 많이 듭니다. Full GC는 Old Generation뿐만 아니라 Young Generation, PermGen/Metaspace까지 포함하여 전체 힙을 대상으로 하는 GC를 의미하기도 합니다.

### 3. 애플리케이션 특성에 따른 GC 튜닝 시 고려사항 및 주요 파라미터

**핵심 정의:** GC 튜닝은 애플리케이션의 응답 시간, 처리량, 메모리 사용량 요구사항에 맞춰 JVM의 GC 동작을 최적화하는 과정입니다.

**고려사항:**

*   **애플리케이션 유형:**
    *   **대화형/실시간 애플리케이션 (예: 웹 서버, UI 애플리케이션):** 짧은 응답 시간과 낮은 지연 시간(Latency)이 중요하므로, STW 시간을 최소화하는 GC (예: G1, ZGC, Shenandoah)를 고려하고 Young Generation 크기를 적절히 조절하여 Minor GC 빈도를 관리합니다.
    *   **배치/처리량 중심 애플리케이션 (예: 데이터 분석, 배치 작업):** 전체 작업 처리량(Throughput)이 중요하므로, STW 시간이 길더라도 전체적인 GC 오버헤드가 낮은 GC (예: Parallel GC)를 고려할 수 있습니다.
*   **객체 생명 주기:**
    *   단명 객체가 많은 경우 Young Generation을 크게 하여 Minor GC 효율을 높입니다.
    *   장명 객체가 많은 경우 Old Generation을 크게 하여 Major GC 빈도를 줄입니다.
*   **메모리 사용 패턴:**
    *   객체 할당 속도, 객체 크기 분포, 참조 패턴 등을 분석하여 GC 알고리즘 선택 및 힙 영역 크기를 결정합니다.
*   **하드웨어 자원:** CPU 코어 수, 사용 가능한 RAM 크기 등을 고려하여 GC 스레드 수 및 힙 크기를 설정합니다.

**주요 파라미터:**

*   **힙 크기 관련:**
    *   `-Xms<size>`: JVM 시작 시 힙의 초기 크기 설정.
    *   `-Xmx<size>`: JVM이 사용할 수 있는 힙의 최대 크기 설정. 일반적으로 `-Xms`와 `-Xmx`를 동일하게 설정하여 힙 크기 조절에 따른 오버헤드를 줄입니다.
*   **Young Generation 크기 관련:**
    *   `-Xmn<size>`: Young Generation의 크기를 직접 설정합니다.
    *   `-XX:NewRatio=<ratio>`: Old Generation과 Young Generation의 비율을 설정합니다 (예: `NewRatio=2`는 Old:Young = 2:1).
    *   `-XX:SurvivorRatio=<ratio>`: Eden과 Survivor 영역의 비율을 설정합니다 (예: `SurvivorRatio=8`은 Eden:S0:S1 = 8:1:1).
*   **GC 알고리즘 선택:**
    *   `-XX:+UseSerialGC`: Serial GC (단일 스레드, 주로 클라이언트 환경 또는 작은 힙).
    *   `-XX:+UseParallelGC`: Parallel GC (처리량 중심, 멀티 스레드 Young/Old GC).
    *   `-XX:+UseParallelOldGC`: Parallel GC와 함께 Parallel Old GC를 사용합니다.
    *   `-XX:+UseConcMarkSweepGC`: CMS GC (낮은 지연 시간, Old GC를 백그라운드에서 수행, Java 9부터 Deprecated).
    *   `-XX:+UseG1GC`: G1 GC (낮은 지연 시간 및 높은 처리량, 큰 힙에 적합, Java 9+ 기본 GC).
    *   `-XX:+UseZGC`: ZGC (매우 낮은 지연 시간, 대용량 힙에 적합, Java 11+).
    *   `-XX:+UseShenandoahGC`: Shenandoah GC (매우 낮은 지연 시간, 대용량 힙에 적합, Java 12+).
*   **기타 튜닝 파라미터:**
    *   `-XX:MaxTenuringThreshold=<threshold>`: Young Generation에서 Old Generation으로 객체가 승격되기까지 Minor GC를 견딜 수 있는 최대 횟수.
    *   `-XX:InitiatingHeapOccupancyPercent=<percent>`: G1 GC에서 Old Generation 사용률이 이 임계값을 넘으면 Concurrent GC 사이클을 시작합니다.
    *   `-XX:MaxGCPauseMillis=<ms>`: G1 GC에서 목표로 하는 최대 STW 일시 정지 시간.

### 멘토의 추가 조언:

GC 튜닝은 단순히 파라미터를 변경하는 것을 넘어, 애플리케이션의 동작 방식과 객체 생명 주기를 깊이 이해하는 것이 중요합니다. 다음 단계를 따르는 것을 권장합니다.

1.  **모니터링:** `jstat`, `jmap`, `VisualVM`, `GCViewer` 등 도구를 사용하여 현재 GC 동작을 분석하고 병목 지점을 식별합니다.
2.  **기준 설정:** 튜닝 전후 성능을 비교할 수 있는 명확한 성능 지표(응답 시간, 처리량, CPU 사용률 등)를 설정합니다.
3.  **점진적 변경:** 한 번에 여러 파라미터를 변경하기보다, 한두 가지 파라미터만 변경하고 결과를 측정하여 어떤 변경이 효과가 있었는지 파악합니다.
4.  **부하 테스트:** 실제 운영 환경과 유사한 부하를 주면서 튜닝 결과를 검증합니다.
5.  **최신 GC 활용:** 가능하다면 G1, ZGC, Shenandoah와 같은 최신 GC를 우선적으로 고려하는 것이 좋습니다. 이들은 대부분의 시나리오에서 좋은 성능을 제공하며, 튜닝이 비교적 용이합니다.

GC 튜닝은 반복적인 과정이며, 애플리케이션의 변화에 따라 지속적으로 모니터링하고 조정해야 할 수 있습니다.
