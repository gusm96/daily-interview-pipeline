## Spring MVC 요청 처리 흐름 및 확장 지점

안녕하세요! Spring MVC의 요청 처리 흐름은 백엔드 개발자에게 매우 중요한 개념입니다. 클라이언트 요청부터 응답까지의 과정을 이해하고, 적절한 확장 지점을 활용하는 것은 견고하고 유연한 애플리케이션을 만드는 데 필수적입니다.

### 1. Spring MVC 요청 처리 흐름

Spring MVC에서 클라이언트 요청이 들어와 응답이 반환되기까지의 전체 처리 흐름은 다음과 같습니다.

1.  **클라이언트 요청**: 웹 브라우저나 다른 클라이언트가 특정 URL로 HTTP 요청을 보냅니다.
2.  **DispatcherServlet**: 모든 요청은 `DispatcherServlet`으로 먼저 전달됩니다. `DispatcherServlet`은 Spring MVC의 Front Controller 역할을 합니다.
3.  **HandlerMapping**: `DispatcherServlet`은 `HandlerMapping`에게 요청을 처리할 핸들러(주로 `@Controller`의 메서드)를 찾아달라고 요청합니다. `HandlerMapping`은 요청 URL과 매핑되는 핸들러를 찾아 반환합니다.
4.  **HandlerAdapter**: `DispatcherServlet`은 찾아낸 핸들러를 직접 실행하지 않고, `HandlerAdapter`에게 핸들러 실행을 위임합니다. `HandlerAdapter`는 다양한 타입의 핸들러를 실행할 수 있도록 추상화된 인터페이스를 제공합니다.
5.  **Controller 실행**: `HandlerAdapter`는 실제 컨트롤러의 메서드를 호출하여 비즈니스 로직을 수행합니다. 컨트롤러는 일반적으로 서비스 계층을 호출하여 데이터를 처리하고, `ModelAndView` 객체나 데이터를 반환합니다.
6.  **ModelAndView 반환**: 컨트롤러는 논리적인 뷰 이름과 모델 데이터를 담은 `ModelAndView` 객체를 반환하거나, `@ResponseBody`를 통해 직접 데이터를 반환합니다.
7.  **ViewResolver**: `DispatcherServlet`은 컨트롤러가 반환한 논리적인 뷰 이름을 `ViewResolver`에게 전달하여 실제 뷰 객체(예: JSP, Thymeleaf 템플릿)를 찾아달라고 요청합니다.
8.  **View 렌더링**: `ViewResolver`가 반환한 `View` 객체는 모델 데이터를 사용하여 최종 응답 페이지를 렌더링합니다.
9.  **응답 반환**: `DispatcherServlet`은 렌더링된 결과를 HTTP 응답으로 클라이언트에게 반환합니다.

### 2. 개발자가 로직을 추가하거나 변경할 수 있는 주요 확장 지점

Spring MVC는 개발자가 요청 처리 흐름 중간에 로직을 추가하거나 변경할 수 있도록 다양한 확장 지점을 제공합니다. 주요 확장 지점과 활용 예시는 다음과 같습니다.

*   **Filter (서블릿 필터)**
    *   **정의**: 서블릿 컨테이너 레벨에서 동작하며, `DispatcherServlet`으로 요청이 도달하기 전/후에 동작합니다. 여러 필터를 체인 형태로 구성할 수 있습니다.
    *   **동작 원리**: `javax.servlet.Filter` 인터페이스를 구현하며, `doFilter()` 메서드에서 요청/응답을 가로채어 처리합니다. `chain.doFilter()`를 호출하여 다음 필터 또는 서블릿으로 요청을 전달합니다.
    *   **활용 예시**:
        *   **인코딩 설정**: 모든 요청에 대해 문자 인코딩을 UTF-8로 설정합니다.
        *   **보안/인증**: 로그인 여부, 특정 IP 접근 제한 등 기본적인 보안 검사를 수행합니다.
        *   **로깅**: 모든 요청에 대한 접근 로그를 남깁니다.
        *   **XSS 방어**: 요청 파라미터에서 스크립트 태그를 필터링합니다.
    *   **주의할 점**: `DispatcherServlet` 이전에 동작하므로 Spring Context의 빈을 직접 주입받아 사용하기 어렵습니다.

*   **Interceptor (Spring 인터셉터)**
    *   **정의**: Spring MVC 프레임워크 내에서 동작하며, `DispatcherServlet`이 핸들러를 호출하기 전/후에 로직을 추가할 수 있습니다.
    *   **동작 원리**: `org.springframework.web.servlet.HandlerInterceptor` 인터페이스를 구현하며, `preHandle()`, `postHandle()`, `afterCompletion()` 세 가지 메서드를 제공합니다.
        *   `preHandle()`: 컨트롤러 실행 전 호출됩니다. (인증/인가, 로깅 등)
        *   `postHandle()`: 컨트롤러 실행 후, 뷰 렌더링 전 호출됩니다. (모델 데이터 조작, 공통 데이터 추가 등)
        *   `afterCompletion()`: 뷰 렌더링 완료 후 호출됩니다. (자원 해제, 예외 로깅 등)
    *   **활용 예시**:
        *   **로그인 세션 체크**: 특정 페이지 접근 시 로그인 여부를 확인하고, 로그인되어 있지 않으면 로그인 페이지로 리다이렉트합니다.
        *   **권한 검사**: 사용자 역할에 따라 특정 기능에 대한 접근 권한을 확인합니다.
        *   **공통 데이터 추가**: 모든 뷰에 공통으로 필요한 데이터(예: 사용자 정보, 알림 메시지)를 모델에 추가합니다.
        *   **API 호출 시간 측정**: `preHandle`에서 시작 시간을 기록하고 `afterCompletion`에서 종료 시간을 기록하여 API 처리 시간을 측정합니다.
    *   **주의할 점**: `DispatcherServlet` 이후에 동작하므로 Spring Context의 빈을 주입받아 활용하기 용이합니다.

*   **AOP (Aspect-Oriented Programming)**
    *   **정의**: 핵심 비즈니스 로직과 횡단 관심사(Cross-cutting Concerns)를 분리하여 모듈화하는 프로그래밍 패러다임입니다. Spring AOP는 프록시 기반으로 동작합니다.
    *   **동작 원리**: `Aspect`는 `Advice`(언제 실행할지)와 `Pointcut`(어디에 적용할지)으로 구성됩니다. Spring AOP는 런타임에 프록시 객체를 생성하여 대상 객체의 메서드 호출을 가로채 `Advice`를 실행합니다.
    *   **활용 예시**:
        *   **트랜잭션 관리**: `@Transactional` 어노테이션을 통해 선언적으로 트랜잭션을 적용합니다. 이는 Spring AOP의 대표적인 활용 사례입니다.
        *   **메서드 실행 시간 측정**: 특정 서비스 메서드의 실행 시간을 측정하여 성능 모니터링에 활용합니다.
        *   **로깅**: 특정 메서드 호출 전후에 파라미터나 반환 값을 로깅합니다.
        *   **예외 처리**: 특정 예외 발생 시 공통적인 예외 처리 로직을 적용합니다.
    *   **주의할 점**: Spring AOP는 기본적으로 프록시 기반이므로, 대상 객체의 내부 호출(self-invocation)에는 적용되지 않습니다. 또한, AOP를 과도하게 사용하면 코드의 흐름을 추적하기 어려워질 수 있습니다.

이 외에도 Spring MVC는 `ControllerAdvice`를 통한 전역 예외 처리, `ArgumentResolver`를 통한 커스텀 파라미터 바인딩 등 다양한 확장 지점을 제공합니다. 각 확장 지점의 특징과 동작 시점을 정확히 이해하고, 애플리케이션의 요구사항에 맞춰 적절하게 활용하는 것이 중요합니다.
