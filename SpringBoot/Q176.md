## Spring 빈 스코프

### 1. 핵심 정의

Spring 빈 스코프는 Spring 컨테이너가 빈의 인스턴스를 생성하고 관리하는 방식을 정의합니다. 즉, 특정 빈의 인스턴스가 언제 생성되고, 얼마나 많은 인스턴스가 존재하며, 언제 소멸되는지를 결정하는 규칙입니다.

### 2. 동작 원리 및 활용

Spring은 다양한 내장 스코프를 제공하며, 각각의 동작 원리와 활용 시나리오는 다음과 같습니다.

*   **Singleton (기본 스코프)**
    *   **동작 원리:** Spring 컨테이너당 단 하나의 빈 인스턴스만 생성하고 관리합니다. 모든 요청에 대해 동일한 인스턴스를 반환합니다.
    *   **활용:** 대부분의 서비스, DAO, 유틸리티 클래스 등 상태를 가지지 않거나 공유 가능한 상태를 가지는 객체에 적합합니다. 애플리케이션 전반에 걸쳐 공유되어야 하는 객체에 사용됩니다.
*   **Prototype**
    *   **동작 원리:** 빈을 요청할 때마다 Spring 컨테이너가 새로운 인스턴스를 생성하여 반환합니다. 컨테이너는 생성까지만 관여하고, 이후의 생명주기 관리는 클라이언트에게 위임됩니다.
    *   **활용:** 각 요청마다 독립적인 상태를 가져야 하는 객체, 예를 들어 다중 스레드 환경에서 스레드별로 독립적인 작업 객체가 필요할 때 유용합니다.
*   **Request**
    *   **동작 원리:** HTTP 요청당 하나의 빈 인스턴스가 생성되고, 해당 요청이 완료되면 소멸됩니다. 웹 환경에서만 유효합니다.
    *   **활용:** 웹 요청과 관련된 데이터를 저장하거나, 요청별로 고유한 상태를 유지해야 하는 객체(예: 현재 로그인한 사용자 정보, 요청 파라미터 등)에 적합합니다.
*   **Session**
    *   **동작 원리:** HTTP 세션당 하나의 빈 인스턴스가 생성되고, 해당 세션이 종료되면 소멸됩니다. 웹 환경에서만 유효합니다.
    *   **활용:** 사용자 세션 전반에 걸쳐 유지되어야 하는 데이터(예: 장바구니, 사용자 설정 등)를 저장하는 객체에 유용합니다.

### 3. 스코프 선택 시 고려해야 할 트레이드오프

스코프 선택은 애플리케이션의 성능, 메모리 사용량, 동시성 문제 등 여러 측면에 영향을 미치므로 신중하게 고려해야 합니다.

*   **메모리 사용량:**
    *   `Singleton`은 가장 적은 메모리를 사용하지만, 잘못된 상태 관리는 동시성 문제를 야기할 수 있습니다.
    *   `Prototype`, `Request`, `Session` 스코프는 요청/세션마다 새로운 인스턴스를 생성하므로 메모리 사용량이 증가할 수 있습니다.
*   **성능 오버헤드:**
    *   `Singleton`은 인스턴스 생성 비용이 한 번만 발생하므로 성능상 이점이 있습니다.
    *   `Prototype`은 요청마다 인스턴스를 생성하므로 생성 비용이 반복적으로 발생하여 성능 오버헤드가 있을 수 있습니다.
*   **동시성 및 상태 관리:**
    *   `Singleton` 빈은 기본적으로 스레드 안전하지 않으므로, 공유 상태를 가질 경우 동기화 메커니즘을 적용하거나 불변 객체로 설계해야 합니다.
    *   `Prototype`, `Request`, `Session` 스코프는 각 인스턴스가 독립적인 상태를 가지므로 동시성 문제로부터 비교적 자유롭습니다.
*   **생명주기 관리:**
    *   `Singleton`은 Spring 컨테이너가 전적으로 생명주기를 관리합니다.
    *   `Prototype`은 컨테이너가 생성까지만 관여하고, 소멸은 클라이언트에게 위임되므로 자원 해제에 주의해야 합니다.
    *   `Request`, `Session`은 웹 요청/세션의 생명주기에 따라 관리됩니다.

일반적으로 특별한 이유가 없다면 `Singleton` 스코프를 사용하는 것이 권장됩니다. 상태를 가지는 빈이 필요하거나, 각 요청/세션마다 독립적인 객체가 필요한 경우에만 다른 스코프를 고려해야 합니다.
